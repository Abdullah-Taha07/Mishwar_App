اختبارات API المتكاملة تمر عبر Workers الراكب والكابتن/الخادم والإدارة **المبنية من المصدر الحالي**. التسجيل والدخول والكوكي والصلاحيات والحجز والتوزيع والحالات والدفاتر تنفذ المعالجات الفعلية. تُطبّق ترحيلات D1 الحقيقية على SQLite جديدة في الذاكرة لكل اختبار باستخدام موصل D1 المحلي الموجود في المشروع ومعاملات `DB.batch` ذرية.

اختبار متصفح الراكب يستخدم بوابات ومصادقة وSQLite فعلية محليًا مع مزودي GPS/طرق/SMS للاختبار. اختبارا واجهتي الكابتن والإدارة يستخدمان الملفات الفعلية والنقر الحقيقي مع API محلية بديلة معلنة؛ يقاسان منفصلين عن دليل Worker/قاعدة البيانات. لا يُدعى اختبار رحلة واحدة بالنقر في ثلاث واجهات مستقلة في الوقت نفسه أو اختبار أجهزة فعلية.

## الأعطال المثبتة والإصلاح

### 1. إنهاء الرحلة قبل إكمال المحطات

قبل الإصلاح، أعاد `trip_status: completed` نجاحًا لرحلة جارية ذات محطتين معلقتين وسمح بالتسوية. فشل اختبارا إعادة الإنتاج **0/2**.

أضيف رفض `409/STOP_SEQUENCE_CONFLICT` حتى مغادرة كل المحطات، وحارس SQL داخل **معاملة التسوية نفسها**. عند تغير الأدلة بين القراءة والكتابة تُلغى المعاملة كاملة، بما فيها سجل الإنهاء والقيود المالية. يستعمل الحارس قيد `NOT NULL` الموجود، بلا ترحيل جديد. زر الإنهاء لدى الكابتن يُعطل مع تفسير السبب؛ يبقى الخادم صاحب القرار.

تحقق الانحدار من رفض المغادرة قبل الوصول وتجاوز محطة، وعدم التسوية عند الوصول فقط أو بعد مغادرة الأولى، ونجاح التسوية مرة واحدة بعد الأخيرة، وفشل سباق داخل الكتابة دون أثر مالي.

### 2. توقف ETA حتى بعد آخر محطة

كانت خدمة التتبع ترد `stops_progress_unavailable` لأي رحلة لها محطات حتى بعد اكتمال مغادرتها. أصبحت تحسب الطريق للوجهة النهائية من مزود الطريق المعتمد بعد آخر مغادرة، وتربط الطلب والذاكرة المؤقتة ببصمة تقدم المحطات. تعاد مراجعة الرحلة وGPS والبصمة بعد رد المزود وداخل كتابة الذاكرة المؤقتة؛ لا يحيي رد متأخر تقديرًا قديمًا.

**المتبقي:** أثناء وجود محطة معلقة يظل ETA غير متاح صراحة. لم ينفذ تقدير إلى المحطة التالية أو إدراج زمن انتظار مستقبلي أو رسم مسافة مستقيمة بدل طريق قيادة. الوصول والمغادرة لا يعيدان التسعير ولا يضيفان رسوم انتظار تلقائية.

### 3. اختلاف بيانات وتحديث تفاصيل الإدارة

أظهر الاختبار المتكامل غياب `stopProgress` من تفاصيل الإدارة مع وجوده لدى الراكب والكابتن. كان التسلسل يعرض مفاتيح أحداث المحطات دون أسمائها العربية، والتفصيل المفتوح لا يواكب تقدمها تلقائيًا.

أضيفت قراءة محمية تستعمل عقد المحطات وسياسة التتبع نفسيهما: `options.stops` و`stopProgress` و`driverLocation` و`eta`. تظهر أسماء المحطات وترتيبها وأوقات الوصول والمغادرة والانتظار المسجل والأحداث العربية. يتحدث التفصيل كل 8 ثوانٍ، وعند العودة للاتصال/حدث التحديث، دون استبدال نماذج الصفحات الأخرى.

تُقيّد الطلبات بالمالك والصفحة والنافذة وتسلسل القراءة، وتُلغى عند الإغلاق أو تبديل الحساب. تراجع حداثة GPS/ETA محليًا كل ثانية؛ عند انقطاع التحديث يُخفى التقدير المباشر وتتاح إعادة **قراءة** فقط. اكتمال الرحلة أو إلغاؤها يغلق GPS/ETA ويمسح ذاكرتهما الخاصة. القيم التي يكتبها المستخدم تُهرب قبل HTML.

اسم الكابتن غير موجود في استعلام الإدارة القديم، وبقيت الواجهة تعرض المعرّف بديلًا إن غاب الاسم؛ ليس ذلك تراجعًا جديدًا ولا ادعاء اكتمال تحسين بيانات الهوية.

### 4. مراجعة RDEV-006 دون إعادة بنائه

حارس المطابقة الموجود لم يظهر به عطل إضافي، ولم يُعدل `refunds.js`. الاختبار القديم يحاكي قيد SQL؛ الاختبار الجديد ينفذ الاسترداد الفعلي عبر بوابتي الراكب والإدارة، مع بديل مزود معلن:

1. دفع محلي تجريبي وتأكيده مرتين دون تكرار الرصيد، ثم حجز وإلغاء.
2. حجز مبلغ الاسترداد مرة واحدة ورفض طلب مكرر أو حساب آخر.
3. محاكاة ضياع رد إرسال المزود: الحالة `submitted_unknown`، وطلب POST واحد فقط، ولا إعادة إرسال تلقائية.
4. تداخل طلبي GET للمطابقة؛ مطالبة إتمام واحدة وقيدان متوازنان فقط، ولا ائتمان مكرر.

هذا يثبت عدم التراجع في حارس RDEV-006 محليًا، ولا يعني أن استردادًا بنكيًا حدث أو أن Sandbox معتمد.
