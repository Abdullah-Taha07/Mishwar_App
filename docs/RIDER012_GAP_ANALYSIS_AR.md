# RIDER-012 — تحليل فجوات تجربة الراكب

تاريخ المراجعة: **20 نوفمبر 2026**. الأساس المحفوظ: `4ad7dda0b5159375e510e7bced73ce2d03b7b108`، مع تعديلات RIDER-012 المحلية في فرع `work/rider-012-readiness-20261120`. هذه مراجعة للكود والأدلة الموجودة؛ لم تُشغَّل اختبارات أو اتصالات جديدة من أجل إعداد الوثيقة، ولم تُعدَّل خدمات أو بيانات بعيدة.

**النتيجة: اجتازت النسخة الحالية القبول المحلي: 557/557 اختبار تطبيقات و64/64 سيناريو متصفح، لكن الجاهزية التجارية ونجاح رحلة ميدانية متكاملة لم يُثبتا.** المقارنة هنا مع معايير تجربة الركوب التي طلبها المستخدم في مرفق RIDER-012، وليست ادعاءً عن خصائص أو أداء إصدار حالي من Uber. تحافظ التعديلات على هوية مشوار البترولية والتركواز، دون نسخ هوية منتج آخر.

## طريقة التصنيف وحدود الدليل

التصنيفات الخمسة المطلوبة هي: **مكتملة ومختبرة**، **موجودة ولكن تحتاج تحسين**، **موجودة ولكن معطلة**، **غير موجودة وتحتاج تطوير**، **تحتاج خدمة خارجية أو اختبارًا فعليًا**. يوضح كل صف حدود تصنيفه؛ وصف «مكتملة ومختبرة» يخص السيناريو المحلي المذكور فقط، ولا يشمل تلقائيًا الأجهزة أو الخدمات الحقيقية. لا يُستخدم وصف «معطلة» لمجرد أن إعداد مزود بعيد لم يُتحقق منه.

- **P0:** منع تسرب أو فساد بيانات أو تنفيذ مالي غير مأذون؛ حاجز يجب إغلاقه قبل أي تجربة بعيدة أو إطلاق. عزل Preview أثناء التشغيل حاجز مفتوح خارج قبول الواجهة المحلي.
- **P1:** سلامة الحجز والدفع والتتبع واستعادة الخدمة؛ يلزم إثباته ضمن بيئة الإطلاق المعتمدة.
- **P2:** تحسين تجربة أو وظيفة إضافية تحتاج قرار نطاق؛ لا يُضاف نظام كبير ضمن إصلاح واجهة دون تقييم.

أدلة الوحدة والواجهة تستخدم حالات حسابات وGPS ومزودات مصطنعة. تستخدم اختبارات Hub في [fixtures.mjs](../apps/hub/tests/fixtures.mjs) SQLite مستقلة بالذاكرة تُطبَّق عليها ملفات الترحيل المحلية؛ هذا لا يثبت سلوك D1 البعيدة أو موارد الإنتاج. اختبار [cash-journey.test.mjs](../apps/rider/tests/cash-journey.test.mjs) يربط بوابات الراكب والكابتن والإدارة المجمعة بخادم Worker وSQLite محليين، مع وثائق كابتن وهاتف موثّق ومسار مزود مُعدَّة كمتطلبات اختبار، ودون SMS أو دفع أو خرائط حقيقية.

اختبار [rider-readiness-browser.mjs](../scripts/rider-readiness-browser.mjs) يستخدم نقرات متصفح Chromium فعلية على ملفات التطبيق المحلية، لكن API فيه fixture، والخريطة شبكة SVG محايدة، والخطوط ومصادر الشبكة الخارجية مستبدلة محليًا. يبدأ بحساب تجريبي موثّق، ويضبط نقاطًا ومسارًا معروفين في بعض السيناريوهات؛ يسمح بالنقد والمحفظة ويعطّل البطاقة وApple Pay. لا يمثل هذا إتمام بحث وموقع ودفع ورحلة على مزودات حقيقية.

## ترتيب إغلاق الفجوات قبل الإطلاق

1. **حاجز P0 للبيئة:** إثبات عزل Preview أثناء التشغيل عن D1/R2 والأسرار والإنتاج ومنع أي نشر تلقائي غير مقصود. وجود موارد staging أو Previews Base لا يغلق هذا الشرط. لا كتابة بعيدة أو اختبار بيانات حقيقية قبل إثباته والموافقات اللازمة.
2. **قبول النسخة الحالية محليًا — أُنجز:** أُغلقت إخفاقات المؤشر الأربعة بدليل 64/64 اللاحق؛ نجحت اختبارات التطبيقات 557/557، والتشغيل 19/19، والأمان 7/7، وتدقيق المصدر 19/19 كما في الجدول. هذه نتائج التغييرات الحالية، وليست إعادة استخدام نجاح الأساس كبديل عن قبولها.
3. **خدمات P1 على بيئة مستقلة:** TomTom والمسار/الزحام، SMS/استعادة الحساب، اتصال/Realtime وإشعارات، تهيئة دفع Sandbox وتحقق مزود واسترداد، ومجدول الحجوزات عند اعتماده؛ مع تحقق الإعداد الفعلي بدل الاكتفاء بأسماء المتغيرات.
4. **رحلة كاملة والأجهزة:** راكب وكابتن وإدارة بهويات اختبار مأذونة، من اختيار عنوان حتى الإنهاء والتسوية والتقييم، مع إلغاء وعدم توافر كابتن وانقطاع واستئناف وحساب آخر؛ ثم Android وiPhone وSafari وTalkBack وVoiceOver والبطارية والأداء.
5. **قرار نطاق P2:** ETA موثوق، تغيير وجهة رحلة نشطة، وحالات المحطات/الانتظار، وتوسعة PDF/الفوترة إن لزمت. كل منها يحتاج تصميمًا وقبولًا مستقلين؛ لا تُسوَّق كوظائف منفذة بمجرد وجود زر أو نص.

لا تتضمن هذه الوثيقة تصريح Push أو نشر أو ترحيل أو تغيير مالي، ولا إعلان جاهزية 100%. تبقى بيانات العملاء والإنتاج خارج الاختبار، وتبقى جميع الأعمال السابقة والنسخ الاحتياطية محفوظة.
