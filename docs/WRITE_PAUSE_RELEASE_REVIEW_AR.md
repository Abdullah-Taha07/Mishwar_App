# مراجعة إيقاف الكتابة وخطة إصدار D1 وWorker

التاريخ: 16 نوفمبر 2026. مراجعة مصدر ثابتة عند `9e9b460`، تتبع خطة `docs/D1_WORKER_RELEASE_PLAN_AR.md`. أُجريت قراءة محلية فقط؛ لم يُنشر Worker أو تُعدّل D1/R2 أو أسرار أو جلسات إنتاجية، ولم تُعَد الاختبارات الناجحة السابقة. هذه مراجعة أُعدت محليًا دون تعديل المصدر أو الأربعة الأصلية؛ أُدرجت لاحقًا في توثيق الاستئناف، دون رفع.

**القرار: ⏳ No-Go للإنتاج حاليًا.** الخطة تضع ترتيبًا صحيحًا للترحيل والنشر والتراجع، لكن لا توجد في المصدر آلية شاملة ومثبتة لتجميد جميع الكتابات وتصريف الأعمال الجارية. نجاح استعادة نسخة محليًا لا يغلق هذا الشرط.

## حصر الكتّاب والمداخل

النطاق يشمل جميع وحدات المصدر التي ظهر فيها SQL لتعديل البيانات أو R2 أو عمل مؤجل، مع الآثار الجانبية للمزودين:

| المجموعة | المداخل | الوحدات والكتابة |
|---|---|---|
| بوابة الراكب | Vercel API ونسخة Worker في `apps/rider`، ثم `/internal/rider-auth` و`/internal/live-rider` و`/internal/rider` و`/internal/rider-background` و`/internal/route-estimate` و`/internal/places/*` | الوكيل لا يلغي كتابة الخادم؛ يخدم أيضًا إجراءات جلسة/مراقبة/تقدير قد تكتب |
| بوابة الكابتن | Vercel rewrite أو Worker مباشرة؛ `/api/auth/*`، `/api/driver`، `/api/application`، `/api/captain-presence`، `/api/background`، `/api/documents/renew` | يجب تغطية العنوان المباشر وكل عنوان يسمح بالوصول إليه، لا عنوان Vercel وحده |
| بوابة الإدارة | Vercel `apps/admin/api/admin/*` و`admin-auth/*`، وWorker الإدارة القديم، ثم `/internal/administration/*` | إنشاء/نشاط/إلغاء جلسات الموظفين والتدقيق قد يكتب؛ جميع مسارات الإدارة مشمولة دون تغيير صلاحيات الموظفين |
| الهوية والجلسات | التسجيل، الدخول، الخروج، التحقق، استعادة/تعديل الحساب | `free-auth.js`، `rider-auth.js`، `public-phone-otp.js`، `email-auth.js`، `account-settings.js`، `recovery.js`، `staff-security.js`: حسابات وجلسات ورموز وحدود معدل وتدقيق، وإرسال SMS/بريد خارجي |
| الرحلات والمحفظة والتشغيل | إجراءات الراكب والكابتن والإدارة وwebhook | `commerce.js`، `operations.js`، `dispatch.js`، `negotiation.js`، `refunds.js`، `recharge.js`، `referrals.js`، `trip-extras.js`: حجز/إسناد/إلغاء/تحصيل، دفتر وتسويات، قبول وعروض وGPS ومكافآت واستردادات |
| الدعم والإطلاق والتوسع | محادثات/تذاكر/بلاغات/حجوزات/إيصالات وقرارات الإدارة | `launch-features.js`، `launch-operations.js`، `message-requests.js`، `expansion.js`، `admin.js`: رسائل وتذاكر وإيصالات وضوابط وتدقيق ومراجعات |
| التقدير والخرائط | تقدير طريق وبحث/جيوكودنج حتى للضيف | `routing.js` و`commercial-maps.js`: حصص طلبات، cache ونتائج طريق/تقدير؛ ليست قراءة خامًا فقط |
| الإشعارات والاتصال | تسجيل اشتراك/جهاز، تأكيد قراءة، الإرسال المؤجل | `background.js` و`native-push.js`: إشعارات واشتراكات وأجهزة، حذف الاشتراك غير الصالح؛ `realtime.js`: نشر خارجي قد يستمر بعد HTTP |
| المستندات والنسخ | تسجيل/تجديد وثائق، إنشاء/فحص نسخة الإدارة | `index.js`، `document-renewal.js`، `launch-operations.js`: R2 put/delete وتسجيل/تحديث D1. تنزيل R2 للقراءة لا يضمن غياب تدقيق في الطلب نفسه |
| Cron/التشغيل اليدوي | `scheduled` كل دقيقة من الإعداد، أو إدارة `reservations` | `runPlatformJobs` ينهي المطابقة وينفذ الحجوزات ويفرّغ حصص/metrics ويضيف `job_runs` وإشعارات |

توجد كذلك كتابات غير مباشرة داخل SQL triggers، مثل تحديث رصيد المحفظة وإجراءات AUTOINCREMENT. يجب إثبات توقف **المعاملة الأصلية** لا الاكتفاء بمراقبة استدعاء `UPDATE` في JavaScript.

## التصميم المقترح قبل طلب موافقة إنتاجية

هذه متطلبات تنفيذ/اختبار مستقبلية محلية، لا وصف لميزة موجودة ولا إذن لإنشائها في الإنتاج:

1. **حالتان منفصلتان للتصريف والتجميد.** `open → draining → frozen → validating → open`. أثناء التصريف تتوقف الحجوزات/الدفعات الجديدة أولًا، وتكتمل الرحلات والأعمال المقبولة مسبقًا وفق إجراء تشغيلي معلوم. لا تبدأ صيانة قاعدة أثناء رحلة فعلية نشطة دون خطة خدمة وسلامة معتمدة.
2. **بوابة خادم مركزية قبل الأثر الجانبي.** توضع قبل التوثيق الذي يكتب الحصص/التدقيق، وقبل توجيه webhook أو أي `/api` أو `/internal`، وقبل إضافة `request_metrics`. تغطي أيضًا `scheduled` والتشغيل اليدوي، وتستخدم حالة موحدة ذات generation/epoch دون cache متساهل. فشل قراءة حالة الصيانة يمنع الكتابة. لا يسمح Header يرسله المتصفح أو مفتاح الخدمة العادي بتجاوزها.
3. **قائمة سماح صغيرة مثبتة القراءة فقط.** ملفات الصيانة الثابتة، preflight اللازم، وفحص حالة صيانة مستقل بلا metrics/تدقيق داخل D1. لا يُسمح تلقائيًا بكل GET أو إجراء `watch` أو `session` أو لوحة الإدارة. ترجع العمليات المتوقفة `503` و`Retry-After` وتحافظ الواجهات على المسودات ومفاتيح منع التكرار دون إعادة محاولة مالية تلقائية.
4. **منع السباق عند الالتزام، لا فحص المدخل فقط.** قد يصل رد مزود بعد تغير الوضع؛ لذلك يجب إعادة الفحص قبل إرسال أثر خارجي وبعد كل انتظار طويل، مع حارس داخل كل معاملة كتابة في D1. تصميم مرشح على D1 الموجودة: حالة صيانة ذات epoch، وحارس ذري في بداية `DB.batch` يرفع خطأ عند تجميد الكتابة أو قدم epoch، فتتراجع الدفعة كلها. مجرد `SELECT` قبل `await` أو إدراج مشروط يعيد صفر صفوف ثم متابعة بقية SQL غير كافٍ. تُحصر وتُحوّل استدعاءات التعديل المفردة والدفعات في الوحدات المذكورة، بما فيها التدقيق والقياس والتنظيف. إضافة جدول/حارس ستكون تغييرًا مستقلًا يحتاج مراجعة وترخيصًا قبل أي تطبيق إنتاجي.
5. **تصريف قابل للقياس للأعمال المقبولة.** تتبع العمليات الجارية و`waitUntil` والرفع/حذف R2 والتسوية المالية بمعرفات لا تتضمن بيانات شخصية؛ تضمين مهلة إلغاء وepoch يمنع عودة كاتب قديم بعد مهلة. لا يُعتبر انتظار عدد ثابت من الثواني أو رقم عداد داخل ذاكرة isolate واحدة دليل تصريف موزع. الوصول إلى `frozen` يحتاج خلو الأعمال المعترف بها وثبات بصمات/عدادات البيانات والآثار الجانبية ضمن فترة اختبار محددة.
6. **webhooks والدفع.** تحقق من إعادة إرسال مزود الدفع فعليًا ومدة احتفاظه وأقصى تأخير، أو اعتمد استقبالًا متينًا منفصلًا للأحداث مع تخزين idempotency ثم معالجة بعد الاستئناف. لا تعِد `200` لحدث لم يُحفظ، ولا تفترض أن `503` يعاد تلقائيًا إلى أجل غير محدود. إذا تعذر إثبات هذه الضمانات، تُمنع النافذة إلى أن تُنهى العمليات المالية المعلقة وتُحدد التسوية. لا تُنشأ خدمة مدفوعة أو Queue خارجية تلقائيًا.
7. **R2 والمزودون.** الطلب الذي رفع ملفًا قبل التجميد يجب أن يكمل تسجيله أو تنظيفه قبل إعلان الخلو. تُسجل عمليات المزود ذات النتائج غير المؤكدة لإعادة المطابقة؛ إيقاف SQL لا يلغي SMS/بريدًا أو دفعًا أُرسل مسبقًا. لا يحذف التراجع ملفات أو يعيد إرسال دفعات تلقائيًا.
8. **الحزم القديمة والمداخل المباشرة.** إثبات عدم وجود نسخة قديمة تستقبل حركة أو مهمة خلفية يمكنها تجاوز الحارس؛ مراجعة aliases وpreview والأصول المباشرة. إجراء تهيئة الصيانة نفسه قد يحتاج تغيير Worker أو مخططًا مساعدًا، ولذلك يجهز ويختبر معزولًا ويعتمد منفصلًا؛ لا يجوز افتراض تفعيله دون نشر.

## اختبارات قبول جديدة لازمة لآلية الصيانة

لم تُنفذ هذه الحالات؛ لا تعاد حزمة الـ404 الناجحة لمجرد المراجعة. بعد تنفيذ آلية الصيانة على موارد محلية/معزولة، تضاف اختبارات موجهة:

| الحالة | معيار النجاح |
|---|---|
| كل مدخل وعنوان مباشر ودور حساب | رفض كل مسار كاتب أثناء frozen مع بقاء الصلاحيات كما هي؛ لا bypass عبر Origin أو Header أو GET |
| `live_watch/session` وmetrics وتدقيق الإدارة | صفر تغييرات D1 رغم استمرار polling؛ القراءة المسموحة لا تكتب سجلًا إضافيًا |
| Cron و`runNow` و`waitUntil` | رفض البدء الجديد؛ وصول عداد الأعمال المقبولة إلى صفر؛ لا كتابة مؤجلة بعد إعلان frozen |
| إيقاف مزود OTP/دفع عند حاجز ثم تبديل epoch وإعادة الرد | الحارس يرفض الالتزام المتأخر بالكامل؛ لا حساب موثق أو قيد محفظة جزئي؛ تصنيف أي أثر خارجي للتسوية |
| سباق تجميد بين أول وآخر عمليات دفعة مالية | كل الدفعة تنجح قبل حد التجميد أو تتراجع كلها؛ لا خصم/رد/إسناد مزدوج |
| رفع R2 قبل/أثناء التجميد وفشل D1 بعد الرفع | انتهاء/تنظيف موثق قبل الخلو؛ لا عمليات R2 لاحقة غير متتبعة، ولا بيانات سرية في السجل |
| تكرار webhook، فقد التأكيد، وإعادة التشغيل | حفظ/إعادة تسليم قابلة للإثبات وتنفيذ مالي واحد، وعدم إسقاط الحدث أو ادعاء النجاح |
| فشل قراءة حالة الصيانة أو سقوط isolate | منع الكتابة عند عدم اليقين، واستعادة العدادات/الالتزامات دون الاعتماد على ذاكرة عملية واحدة |
| انتهاء أعمال حية ثم تطبيق `0022/0023` على نسخة معزولة | ثبات البيانات الأصلية وتسلسل الرسائل والعلاقات، نجاح Worker الموافق على المخطط الجديد، وبقاء بوابة الصيانة صالحة بعد إعادة بناء الجداول |
| الرجوع وإعادة الفتح | إعادة فتح متدرجة بعد فحص الحزمة/المخطط والتسوية؛ لا إعادة تلقائية لمعالجة مالية بمفتاح جديد |

## مراجعة الترحيلات والتراجع

- **`0022` يضيف عمودًا فقط** ويترك `target_email=NULL` للروابط القديمة. لا يُستنتج عنوان البريد القديم، ولا تعاد صلاحية الرموز القديمة. يجب اختبار مسارات الإصدار الذي سيُشغّل فعليًا، لا مجرد وجود العمود.
- **`0023` يعيد بناء جدولين** ويجعل `service_cases.trip_id` قابلًا لـNULL ويضيف حقول وفهارس منع التكرار للرسائل. لا يوجد Down migration آمن يعيد `NOT NULL` بعدما أُنشئت طلبات دعم حساب بلا رحلة؛ قد يحذف بيانات أو يفشل. تبقى هذه بيانات صحيحة بعد النشر ولا يجوز اختلاق رحلة لها.
- مثال النسخة القديمة من Git `origin/main` يقبل إدراج الرسائل دون `client_request_id`، وبالتالي قد يفقد ضمان إعادة المحاولة الجديد، كما أن مسارات دعم المستخدم القديمة ترتبط برحلة. لا يعني نجاح بعض استعلامات الإدارة على NULL أن تجربة الدعم كاملة متوافقة. هذه مراجعة مثال من Git، **وليست إثباتًا لمحتوى Worker الإنتاجي**؛ يجب حفظ الحزمة الفعلية وربط معرفها وبصمتها قبل اعتمادها للتراجع.
- الترتيب في النافذة بعد استيفاء البوابات والموافقة: إثبات frozen → نسخة/Time Travel حديثان وحزمة رجوع محفوظة → `0022` ثم `0023` → Worker الموافق → فحوص مخطط/دعم/هوية/تسوية معزولة ومحددة → الواجهات ثم إعادة الكتابة والوظائف تدريجيًا. فشل الثانية لا يرجع الأولى الناجحة تلقائيًا.
- عند فشل Worker والمخطط سليم، يُرجع فقط إلى **حزمة مثبتة التوافق مع المخطط الأمامي**. إن غاب الدليل تبقى الصيانة ويُحضّر إصلاح أمامي؛ لا استعادة D1 آلية.
- استعادة D1 تحتاج إجراء معتمدًا منفصلًا، ووقف كل الكتّاب والتحقق من نقطة الاستعادة وتوافق الحزمة. بعد إعادة فتح الكتابة لا تُستبدل القاعدة بنسخة قديمة دون حفظ الحالة الأحدث وخطة دلتا وتسوية؛ R2 والمزود المالي لا يرجعان مع D1.

## بوابات No-Go قبل أي طلب إنتاجي

- ✅ أُثبت نجاح Wrangler/D1 محليًا ومقارنة بيانات النسخة، ثم فحص صحة ومخطط مصدر Worker على D1/R2 محليتين. هذا ليس رحلة كاملة أو اختبار R2 إنتاجي؛ التفاصيل في WRANGLER_ISOLATED_RESULT_AR.md.
- ⏳ تنفيذ واختبار تجميد/تصريف شامل مع حارس التزام، وحصر جميع المداخل والوظائف والعمليات الخارجية والمشغلين.
- ⏳ حفظ الحزمة الإنتاجية الفعلية وبصمتها وإعدادات الربط بأسمائها، واختبار توافق الرجوع على المخطط الأمامي بما فيه دعم بلا رحلة وإعادة المحاولة.
- ⏳ ضمانات إعادة تسليم webhook/التسوية، وحالة عدم وجود رحلات أو عمليات مالية لا يمكن تعليقها بأمان.
- ⏳ تحديث نسخة حقيقية ونقطة Time Travel بعد التصريف وقبل نافذة التغيير، وقياس زمن/مساحة إعادة بناء الجدولين؛ لا وعد بتوقف صفري.
