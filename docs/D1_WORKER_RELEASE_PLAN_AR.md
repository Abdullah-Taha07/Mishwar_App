## إعادة التجربة محليًا

بيئة الاختبار المعتمدة لهذا السكربت Node 26.13 وتدعم [SQLite authorizer](https://nodejs.org/api/sqlite.html#databasesetauthorizercallback) وSQLite defensive mode. المثال التالي محلي بالكامل ويستخدم مجلد خرج **جديدًا** داخل مجلد محلي مستبعد من Git:

```powershell
node scripts/d1-migration-rehearsal.mjs 'D:\Mishwar_App\private-backups\verified.sql' 'D:\Mishwar_App\private-backups\rehearsal-unique-id'
node --test scripts/tests/d1-migration-rehearsal.test.mjs
```

المسارات مثال، وليست إثبات وجود ملف. لا يُعاد استخدام مجلد خرج سابق. قاعدة `rehearsal.sqlite` تحتوي بيانات خاصة مثل المصدر؛ تُحفظ محليًا بصلاحيات مناسبة ولا تُرفع إلى Git أو محادثة. تقرير `rehearsal-report.json` يحوي الأعداد وبصمات الصفوف والتسلسل فقط، دون قيم سجلات أو رموز بريد.

يفحص السكربت بصمة SQL قبل وبعد التشغيل، ويرفض `TEST FILE ONLY`، ويمنع `ATTACH` والإضافات و`writable_schema` أثناء الاستعادة. يقارن كل صف عبر الأعمدة الأصلية لكل جدول، ولا يكتفي بعدّ الرسائل. يتحقق من `foreign_key_check` و`integrity_check` محليًا، ومن رفض رسالة يتيمة أو مكررة، ويعيد كل بيانات الاختبار داخل Savepoint. يميز الأعمدة الموجودة مسبقًا ولا يطبق `ALTER TABLE` مرتين. حالة `provenance=unverified-local-input` تعني أن نجاح الاستعادة لا يثبت المصدر الإنتاجي. تمرير `--receipt <مسار الإيصال>` يعيد التحقق من نسختي SQL ونوع `production-export` ومعرف القاعدة ومطابقة بصمة المصدر ومساره، ويربط تقرير التجربة ببصمة الإيصال. فشل `integrity_check` سابقًا عبر D1 بسبب `SQLITE_AUTH` لا يعني فسادًا.

### محاولة Wrangler السابقة واستكمالها المعزول

استُخدم Wrangler المثبت في `C:\Users\User\Mishwar_Wrangler_Export_V2\node_modules\wrangler\bin\wrangler.js` بأوامر `d1 execute` تتضمن `--local` ومسار `--persist-to` جديدًا في `D:\Mishwar_App\private-backups\wrangler-local-20261116\state`. حُفظ stdout/stderr وسجل Wrangler داخل مجلد التجربة الخاص دون طباعة SQL أو السجلات.

انتهت المحاولة السابقة برمز خروج `1` وخطأ `EPIPE`؛ لم تصل إلى الترحيلات. استُكمل العمل الآن بتكوين مستقل ذي معرّف D1 وهمي `00000000-0000-0000-0000-000000000001`، وحالة محلية جديدة في `D:\Mishwar_App\private-backups\wrangler-isolated-sandbox-20261116`. استُخدم مسار workerd الأصلي صراحة عبر `MINIFLARE_WORKERD_PATH` وبيت إعدادات XDG فارغ، وأزيلت بيانات اعتماد Cloudflare من بيئة العملية. لم يُستخدم ملف إعداد الإنتاج أو binding بعيد، وكانت جميع أوامر D1 تتضمن `--local`.

نجحت الخطوات الأربع: فحص الاتصال المحلي، والاستيراد، وتطبيق الترحيلين، وقراءة حالة الترحيلات. فُحص ملف D1 المحلي المحفوظ مستقلاً: جميع الصفوف الأصلية والتسلسل محفوظة، و`foreign_key_check=0` و`integrity_check=ok`، وبصمة SQL الأصلية لم تتغير. الأدلة الوصفية في `.local-verification/WRANGLER_ISOLATED_RESULT.json`؛ السجلات والقاعدة الخاصة بقيت خارج Git. نجاح هذا التكوين يتجاوز عائق التشغيل السابق، ولا يعزل وحده أي متغير كان السبب الوحيد لـ`EPIPE`. لم يُنفذ تصدير جديد أو أمر D1 بعيد أو نشر Worker.

نجح كذلك فحص صحة ومخطط مصدر Worker الفعلي عبر `wrangler dev --local` على loopback، مع D1 وR2 محليتين ودون أسرار أو موارد بعيدة. أعادت `/api/health` الجاهزية، ونجحت الاستعلامات عن الأعمدة الجديدة، ثم أُوقف الخادم وثبت غياب listener مستقلًا. فُصلت إعادة هذا الفحص الناقص عن استيراد D1 الناجح الذي لم يُعَد. [نتيجة التشغيل وحدودها](WRANGLER_ISOLATED_RESULT_AR.md). ليست هذه رحلة كاملة أو تجربة مزودين أو R2 إنتاجية.

## قرار المراجعة الحالي

**لا يُطلب اعتماد إنتاجي الآن.** استُكمل اختبار D1/صحة Worker المحلي، لكن لم تُنفذ أو تُثبت آلية شاملة لإيقاف الكتابة وتصريف العمليات، ولا توافق حزمة الإنتاج الفعلية عند التراجع. [المراجعة التفصيلية](WRITE_PAUSE_RELEASE_REVIEW_AR.md) تحصر كتابات GET/المراقبة والتشغيل اليدوي وCron والأعمال المؤجلة وR2 وردود المزودين، وتحدد متطلبات حارس التزام ذري وepoch واختبارات قبول جديدة قبل إعلان `frozen`.

يتوقف Git Push أيضًا بطلب المالك تجهيز استبعاد رقم الاختبار محليًا دون رفع؛ [الإصلاح المحلي](PRIVACY_SUPPORT_FIX_AR.md) لا يزيل التعرض القديم من التاريخ العام. [تقرير التعرض وخطة الاعتمادات والتاريخ](PUBLIC_HISTORY_SECURITY_REVIEW_AR.md). لم تتغير D1/R2 أو الجلسات أو أسرار الإنتاج.

## بوابات ما قبل طلب الموافقة

1. قراءة الحالة الحالية لـWorker وD1 وR2، وأسماء متغيرات البيئة دون قيمها، وحالة OAuth وصلاحيات الحساب، وقائمة الترحيلات البعيدة. تسجيل البيانات الوصفية فقط.
2. إثبات نسخة حقيقية مستقلة وبصمتها ومساراتها ثم نجاح استعادتها واختبار الترحيلين. تأكيد أن الوقت حديث وأن القاعدة الصحيحة هي `mishwar-db` بالمعرف المعروف، دون اعتبار الملف الوهمي نسخة.
3. اختبار D1 محلي/staging معزول وبنفس SQL؛ فصل binding عن الإنتاج صراحة. مراجعة حجم الرسائل وزمن إعادة البناء والمساحة المتاحة قبل تحديد مدة التوقف.
4. حفظ حزمة Worker الحالية أو وسيلة إعادة نشرها، ومعرف الإصدار وإعدادات bindings والأسرار بأسماء فقط، وCommit واجهات التطبيقات. حفظ نقطة Time Travel صالحة محليًا قبل التغيير. إمكانية Time Travel ومدته وصلاحياته تُفحص من الحساب الفعلي؛ لا يُفترض اشتراك مدفوع.
5. إثبات التوافق العكسي للحزمة السابقة على المخطط الجديد. لا توجد آلية شاملة مثبتة لإيقاف الكتابة: تعطيل Cron لا يمنع `runNow` الإداري، و`watch/session` وبعض GET تكتب بيانات أو تدقيقًا أو metrics. يلزم تصريف `waitUntil` وR2 وردود المزودين، وحارس التزام ذري يمنع عملية قديمة من الكتابة بعد التجميد؛ لا يكفي فحص المدخل أو إخفاء الأزرار. توثق [مراجعة إيقاف الكتابة](WRITE_PAUSE_RELEASE_REVIEW_AR.md) جميع الكتّاب وحالات `open → draining → frozen → validating → open` واختبارات القبول الجديدة المطلوبة. لا يُطلب اعتماد إنتاجي قبل تنفيذ هذه البوابة واختبارها معزولًا وإثبات إعادة تسليم webhooks والتسوية.
6. بناء التطبيقات وتشغيل الاختبارات الشاملة والمتخصصة وEdge/PWA؛ تدوين نتائج R09 الحقيقية منفصلة عن المحاكاة. إخراج أمر الإصدار الفعلي ومعرفاته ومخاطره للمستخدم، ثم انتظار **موافقة صريحة** على D1 وWorker.

## التراجع

- **قبل نشر Worker أو فتح الكتابة:** عند فشل الهجرة، أبقِ الصيانة؛ افحص القائمة والحالة. يمكن ترك `0022` وحده إذا ثبت توافق الحزمة الحالية، أو اختيار استعادة D1 لنقطة ما قبل النافذة بموافقة منفصلة. لا تكتب Down migration ارتجالية تعيد فرض `trip_id NOT NULL`.
- **فشل Worker والمخطط سليم:** التراجع أولًا إلى حزمة مثبتة التوافق مع المخطط الأمامي. لا تغيير لبيانات D1 ولا لأصول R2 بهذا الإجراء. إذا لم يتوفر دليل التوافق، تبقى الخدمة في الصيانة حتى إصلاح الحزمة أو اعتماد استعادة مقترنة.
- **الحاجة لاستعادة D1 قبل إعادة فتح الكتابة:** أبقِ كل الكتّاب متوقفين؛ تحقّق من نقطة الاستعادة والنسخة؛ نفّذ الاستعادة فقط بعد موافقة صريحة، ثم استعد Worker والواجهات المتوافقة وأعد فحص الرسائل والتسلسل والعلاقات والتسويات. استعادة Time Travel تستبدل البيانات القائمة. [توثيق الاستعادة](https://developers.cloudflare.com/d1/reference/time-travel/).
- **بعد إعادة فتح الكتابة:** لا تعُد تلقائيًا إلى نسخة قديمة؛ ستفقد الكتابات اللاحقة. أوقف الكتابة مجددًا، واحفظ أحدث حالة، وحدد الدلتا وأثر الرسائل والدفع والجلسات والملفات، ثم اطلب اعتماد خطة تسوية واسترجاع محددة. R2 ومزود الدفع لا يرجعان مع D1، ولا تُحذف أصولهما تلقائيًا.

استرجاع إصدار Worker لا يسترجع تخزين D1/R2؛ تغيّر مخطط البيانات قد يمنع تشغيل الحزمة القديمة بصورة صحيحة. [توثيق Worker rollback](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/).

لا تُنفّذ هذه الوثيقة أي أمر بعيد. المطلوب من المالك عند الوصول لبوابة الإنتاج: اعتماد نافذة الصيانة وآلية إيقاف الكتابة والموافقة الصريحة على الترحيل والنشر؛ التراجع الإنتاجي يحتاج أيضًا اعتماد الإجراء المحدد.
