# منظومة مشوار — خارطة طريق الانتقال إلى الإنتاج

**الإصدار:** 1.0 — **التاريخ:** 14 نوفمبر 2026
**النطاق:** تطبيق الراكب (`apps/rider`)، تطبيق الكابتن (`apps/hub`)، لوحة الإدارة (`apps/admin`)، خادم Cloudflare Worker، قاعدة D1، تخزين R2.
**الهدف:** تشغيل بيئة تجريبية مستقلة وآمنة، ثم اختبار الأجهزة والتكاملات قبل تجربة ميدانية مرخّصة في الرياض والإطلاق التجاري.

> **تعريف الحالة:** `LOCAL_E2E_REPORTED_PASSED` = أبلغ صاحب المشروع عن نجاح الرحلة محليًا عبر التطبيقات الثلاثة. لا تعني اجتياز جميع الاختبارات الآلية. آخر سجل كان 113/114 في حزمة الكابتن (فشل واحد في `registration.test.mjs`) ولم تُقدَّم نتيجة أحدث تثبت إغلاقه. لا نفترض تفعيل الخدمات التجارية أو وجود تراخيص أو مفاتيح تشغيل.

## بوابة صفر — تثبيت أساس المشروع (مطلوبة قبل نشر Staging)

- [ ] إغلاق اختلاف اختبار الكابتن بين الجلسة الموثّقة (`200`) وغير الموثّقة (`302`) **من دون تخفيف مصادقة الخادم**.
- [ ] تشغيل `npm ci` و`npm test` و`npm run audit:source` داخل فرع الدمج، وتسجيل نتائج الكابتن والراكب والإدارة بصورة مستقلة.
- [ ] الحفاظ على واجهة الكابتن الثابتة (بطاقة 10–90%، سحب ثابت، عدم إعادة رسم الخريطة في أثناء السحب).
- [ ] مراجعة ملفات النسخ الاحتياطية الحساسة، والمفاتيح والأسرار في المستودع وتدوير ما قد يكون تعرض للكشف، دون نسخ قواعد بيانات إنتاجية إلى بيئة التجربة.
- [ ] التحقق من Clean Git Diff وعدم وجود ملفات `*.sql` تحتوي بيانات شخصية أو مفاتيح أو حزم APK أو `.wrangler` ضمن التغييرات الجديدة.
- [ ] فتح مسار متابعة مبكر لترخيص الهيئة العامة للنقل، وأهلية السائقين، وحماية البيانات قبل أي رحلة حقيقية مدفوعة.

**شرط إغلاق البوابة:** جميع الاختبارات واجتياز مراجعة الأمان ووجود نقطة استرجاع موثقة.

## المرحلة 1 — النشر التجريبي الخاص والتزامن الإلكتروني

**الهدف:** بيئة Staging على الإنترنت منفصلة تمامًا عن الإنتاج.

- [ ] إنشاء Worker جديد مستقل (مثال اسم: `mishwar-api-staging`)، وقاعدة D1 خاصة (`mishwar-db-staging`) وR2 خاص (`mishwar-storage-staging`). هذه **أسماء مقترحة وليست موارد منشأة**.
- [ ] نشر 3 واجهات خاصة بتجربة Rider/Captain/Admin على نطاقات تجريبية مختلفة. كل منها يتصل بواجهة API التجريبية وحدها.
- [ ] فصل جميع أسرار Authentica والخرائط والدفع بين البيئتين؛ أي تكامل فعلي مع طرف خارجي يظل غير مفعل حتى تُجهّز مفاتيح تجريبية أو موافقة تفعيل مقصودة.
- [ ] تحديد allowlist لأصول CORS بالاسم؛ منع Preview deployments غير المعتمدة من الوصول إلى Worker الإنتاج.
- [ ] عدم تشغيل migrations `0014–0019` على قاعدة الإنتاج. راجع تسلسل المخطط وطبقه على D1 التجريبية بعد حفظ نسخة صالحة للاستعادة.
- [ ] تفعيل تسجيل أحداث انتقال الرحلة بشكل متسق (Trip ID/Dispatch ID) مع إزالة رقم الهاتف والبيانات الشخصية من السجلات.
- [ ] تشغيل رحلة عبر الإنترنت: راكب يطلب → كابتن متاح يستلم → قبول → وصول → بدء → إنهاء → ظهورها في الإدارة → تطابق المحفظة/السجل.
- [ ] سيناريوهات التزامن: تحديث الحالة في جهازين، طلبان لنفس الكابتن، قبول مزدوج، إعادة تحميل صفحات الثلاثة.

**شرط الاجتياز:** روابط HTTPS الثلاثة تعمل عبر Worker التجريبي وقاعدة D1 التجريبية فقط؛ نجاح رحلة كاملة عبر الإنترنت؛ دليل أن الإنتاج لم يتأثر.

## المرحلة 2 — Android وiPhone على أجهزة فعلية

- [ ] تحديد طبقة تطبيق أصلية أو Capacitor/Flutter/React Native وفق احتياج Push وخدمة الموقع بالخلفية؛ **PWA وحدها لا تضمن الصوت أو GPS عند قفل الهاتف**.
- [ ] تجهيز Android AAB/إصدار اختبار داخلي و iOS TestFlight مع إعدادات التوقيع وحقوق الاستخدام اللازمة.
- [ ] ربط الإشعارات عبر FCM على Android وAPNs على iOS، وفحص صلاحية الإشعارات والصوت في ظروف إغلاق الشاشة، عدم الإزعاج، وتوفير البطارية.
- [ ] تشغيل تتبع الموقع في الخلفية أثناء الرحلة وفق سياسات النظام وصلاحية المستخدم؛ إيقاف التتبع عند انتهاء الغرض.
- [ ] استعادة حالة الرحلة من الخادم عند الانقطاع أو قتل التطبيق؛ منع تكرار القبول والخصم وإكمال الرحلة باستخدام idempotency.
- [ ] اختبار على جهازين فعليين لكل نظام على الأقل؛ توثيق نوع الجهاز، إصدار النظام، أوضاع البطارية ونتائج كل سيناريو.

**شرط الاجتياز:** اختبارات موثقة متكررة لصوت/تنبيه الطلب عند الإمكان مع الشاشة مغلقة، واستمرار التتبع وفق سياسات النظام، واستعادة الرحلة بلا فقد أو ازدواج. ليست هناك ضمانات لصوت التنبيه مع وضع عدم الإزعاج أو حظر الإشعارات.

## المرحلة 3 — الخرائط والبحث بالعربية والتحقق بالجوال

- [ ] تحديد مزود خرائط وجيوكودنج وتوجيه مروري، بمفاتيح Staging محدودة الصلاحية وتكاليف مراقبة.
- [ ] اختبارات بحث بالعربي في الرياض: أسماء الأحياء والطرق، الاختلافات الإملائية، الأرقام العربية واللاتينية، نقاط الالتقاط، الأماكن المزدحمة.
- [ ] ETA يعتمد على طريق فعلي وساعات الذروة متى دعم المزود ذلك؛ عند انقطاع المزود تُعرض حالة واضحة لا تسعيرًا مضللًا بالمسافة الجوية.
- [ ] ضبط قوالب Authentica SMS واستلام رمز دخول فعلي في بيئة اختبار مصرح بها؛ قفل المعدل، صلاحية رمز قصيرة، عدم تسجيل OTP.
- [ ] فحص تجربة التحقق عند تغيير الهاتف أو فقد الشبكة أو إعادة إرسال الرسالة.

**شرط الاجتياز:** أمثلة موثقة على البحث العربي والـETA، ووصول OTP والتحقق من جهة الخادم دون تجاوز للمصادقة.

## المرحلة 4 — Moyasar ومدى وApple Pay والاسترداد والتسوية

- [ ] بدء جميع سيناريوهات الدفع على Moyasar Sandbox بالمفاتيح التجريبية، ولا توضع مفاتيح `sk_*` مطلقًا في المتصفح أو التطبيق.
- [ ] يتحقق الخادم من رقم العملية والمبلغ والعملة والحالة؛ ولا يؤكد رحلة مدفوعة اعتمادًا على الواجهة أو Callback فقط.
- [ ] Webhooks مع تحقق secret وسجلات idempotency، وتجارب النجاح والفشل والدفع المكرر وفقد الاتصال.
- [ ] اختبار `mada` وApple Pay وفق تفعيل الحساب والتوافق مع الجهاز وشهادات Apple المطلوبة، لا افتراض توفرهما إنتاجيًا تلقائيًا.
- [ ] قيود التسوية: قيمة الرحلة / العمولة / ضريبة القيمة المضافة حسب المعالجة المعتمدة / مستحق الكابتن / المبلغ المحجوز / الاسترداد / رسوم التحصيل؛ تطابق دفتر الأستاذ مع كشف مزود الدفع والبنك.
- [ ] تسويات الكباتن والتحويلات البنكية تتم وفق خدمة مرخصة وصلاحيات وموافقات منفصلة عن اعتماد الرحلة؛ منع اعتبار اعتماد الطلب إثبات دفع فعلي.
- [ ] مراجعة متطلبات الفوترة الإلكترونية والفاتورة الضريبية والتعامل مع زاتكا حسب نموذج المنشأة.

**شرط الاجتياز:** مطابقة Sandbox من الدفع حتى الاسترداد والتسوية دون تكرار، ثم موافقة التاجر والاستعداد التنظيمي قبل معاملات حقيقية.

## المرحلة 5 — الأمان والأداء ومراقبة الأعطال والتعافي

- [ ] استكمال أمن الإدارة: تغيير كلمة المرور، استعادتها بضمان ملكية الحساب، MFA، جلسات قابلة للإلغاء، rate limits، مراجعة صلاحيات الموظفين.
- [ ] اختبارات تسرب معلومات الرحلات/الموقع وCSRF/CORS/RBAC وسلامة webhook وتبادل الأسرار؛ فحص تبعيات الويب والأجهزة.
- [ ] ضغط متدرج على البحث والحجز وإرسال الطلب والقبول والتتبع وإجراء التسويات. تحديد عتبات زمن الاستجابة ونسبة الأخطاء وأعداد المستخدمين المستهدفين قبل التجربة.
- [ ] Logging/Tracing/Alerting مع معرّفات ارتباط لا تكشف بيانات حساسة.
- [ ] سياسة نسخ احتياطي مشفرة لـD1/R2 وقواعد الاحتفاظ والتعافي، **واختبار استعادة فعلي في بيئة معزولة**؛ تحديد RPO/RTO واضحين.
- [ ] خطة حوادث تشغيل (Runbook)، مالك للتنبيهات وقرار rollback واضح.

**شرط الاجتياز:** لا ثغرات حرجة مفتوحة؛ تقرير ضغط ناجح ضمن الحدود المتفق عليها؛ استعادة اختبارية مثبتة.

## المرحلة 6 — الترخيص والتشغيل القانوني في السعودية

- [ ] التحقق من **نوع النشاط الرسمي الصحيح** لمشوار مع الهيئة العامة للنقل — الوساطة في نقل الركاب بالسيارات عبر التطبيقات الإلكترونية — والمتطلبات السارية وتحديثاتها. لا تُستبدل المشورة القانونية السعودية بقائمة تقنية.
- [ ] استكمال السجل التجاري والكيان القانوني والعلامة التجارية والتراخيص والتكامل التقني مع الهيئة متى كان مطلوبًا.
- [ ] التحقق من أهلية كل سائق وسيارته وتصاريحه وتأمينه؛ **يوجد قرار منشور من وزارة الموارد البشرية بقصر القيادة عبر تطبيقات توجيه المركبات على السعوديين** ويجب مراجعة التطبيق الساري والاستثناءات إن وجدت.
- [ ] عقود المستخدم والكابتن، الخصوصية وحماية البيانات الشخصية، سياسة الاحتفاظ، الدعم والبلاغات والمفقودات والسلامة.
- [ ] سياسات قبول الكابتن، مراجعة الوثائق وانتهائها، الاعتراضات، الإيقاف، التصعيد للطوارئ، والمراجعة المالية والضريبية.

**شرط الاجتياز:** مستندات وتصاريح قانونية سارية وموافقة واضحة على إجراء رحلات فعلية، قبل تجربة عامة مدفوعة.

## المرحلة 7 — تجربة ميدانية محدودة في الرياض ثم قرار الإطلاق

- [ ] تحديد منطقة أو منطقتين داخل الرياض وفق الترخيص، واختيار مجموعة صغيرة من كباتن مؤهلين ومستخدمين تجريبيين.
- [ ] توثيق رحلة الاختبار الفعلية والتقاط الموقع، الدخول والخروج من المناطق، زمن وصول الطلب والقبول، وتذبذب الشبكة.
- [ ] لوحة مؤشرات أساسية: عدد الطلبات، وصولها للكباتن، القبول، زمن الإسناد، دقة الالتقاط والـETA، إكمال الرحلة، إلغاء الرحلة، الدفع والتسوية، شكاوى، أعطال.
- [ ] إجراء اختبار رسمي لسيناريو البطارية، الشاشة المقفلة، الانقطاع، والتداخل بين رحلتين.
- [ ] مراجعة النتائج يوميًا، معالجة المشكلات، تقييم تجارب العملاء والكباتن، اتخاذ قرار Go/No-Go واضح.

**شرط الاجتياز:** بلوغ أهداف الأداء والتجربة المعرّفة مسبقًا، مع سلامة قانونية ومالية وأمنية وعدم وجود مشاكل حرجة مفتوحة.

## أول 10 أعمال في Sprint 1

1. إغلاق اختبار الـ302/200 والتحقق من جميع اختبارات التطبيقات الثلاثة.
2. أخذ لقطة code baseline والتحقق من وجود أسرار أو بيانات حساسة بمستودع Git.
3. اختيار أسماء موارد Staging وأسماء النطاقات الثلاثة.
4. إعداد قائمة Secrets منفصلة بالاسم فقط، بلا قيم أو نسخ من الإنتاج.
5. إنشاء D1 وR2 مستقلتين مع آلية backup/restore للتجربة.
6. نشر Worker Staging وAPI health تحت عنوان منفصل.
7. تشغيل migrations على قاعدة Staging بعد مراجعة الترتيب والتوافق.
8. نشر واجهات التطبيقات الثلاثة وربطها بWorker Staging فقط.
9. اختبار تسجيل دخول كل دور ورحلة كاملة مع فحص CORS وD1 من الأجهزة.
10. إصدار تقرير Gate 1 يتضمن الأدلة والعيوب والقرار؛ عدم دمج Staging في main تلقائيًا.
